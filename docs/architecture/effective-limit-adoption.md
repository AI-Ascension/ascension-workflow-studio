# Effective-limit capability adoption

This is a bounded companion for Studio #119, Context Console #24 and Harness #95.
It adopts the accepted Console ADR 0020 v1/v3 reader migration. It does not complete
Studio #119's input-budget feature.

## Contract and authority

`contracts/effective-limits.lock.json` pins the four original Harness artifacts at
`f8015e52ccb530e60d722283ef2b063da372169b`, the previous provider capability v1
schema, and original synthetic descriptors/records generated by that Harness
library. The vectors were supplied by Console PR #28 at
`678ae6b19c6dff9875c3e0fbe6d203fcfc615366`; their generator lives at
`tools/effective-limit-fixtures` in that repository.

Studio keeps its existing memory v1 projection reader, including the legacy
owner's optional advisory fields. Provider v1 follows the pinned closed schema
and retains its encryption and method-name restrictions. Both v1 readers return
`field_not_advertised` for executable capacity, regardless of any legacy advisory
schema maxima. The v3 readers validate the complete closed producer schemas,
including required `effective_limits` and `binding`. Unknown versions fail.

Validators are compiled in Node from the pinned schemas into checked-in static
ESM by `tools/generate-effective-limit-validators.mjs`. CI runs its `--check`
mode to reject stale generated code. The browser never invokes Ajv compilation
or `Function`/`eval`; the existing `script-src 'self'` CSP remains unchanged.
The check also executes original producer vectors through the emitted native
ESM module, covering helper interoperability outside Vitest's module loader.

The Context client reads `/v3/memory/capabilities` and
`/v1/runs/{context_run_id}/provider-sessions/capabilities` through its same-origin
Context route. The latter requires a local-metadata-only envelope with zero
inference calls and game effects. The Context run comes from the explicit Harness
association; it is never inferred from the workflow run. Harness retains its
existing authoritative workflow-scoped provider-session inspection route.

There is no advertised effective-limit-record HTTP route. Studio reads the
descriptor's executable values directly and checks every projection against the
original producer record vectors. It does not invent a record endpoint or
reconstruct classification rows to authenticate against themselves. This slice
does not implement pin-matrix record admission; the coordinated Harness
consumer-matrix alignment remains a separate owner change.

## Integrity and admission

Structural validation alone cannot establish a usable limit. Studio checks the
policy digest against its own pinned artifact, adapter/model binding consistency,
and the full descriptor digest before displaying executable capacity. The digest
algorithm is the producer's ordered `serde_json` serialization with
`binding.descriptor_sha256` cleared. It is not sorted-key canonical JSON or the
capabilities-schema digest. The pinned schema property order matches the producer
struct field order; tests check the original library-generated digests on both
surfaces. A future producer serialization change requires coordinated repinning.

The scoped authenticated owner remains the source of the selected descriptor;
an integrity hash alone is not authentication. The client-side preflight accepts
a freshly fetched current descriptor and the earlier preview. A changed
descriptor invalidates the preview; it does not reuse approval across changed
limits, model, adapter, profile or scope. Missing values, disabled memory,
tampered payloads and stale policy pins are unavailable. The owner remains
responsible for full policy validation and dispatch admission.

Refreshing the current association invalidates displayed limits immediately.
Unavailable associations keep them unavailable, and generation guards prevent
older in-flight descriptor responses from restoring superseded claims.

The UI presents bytes as bytes and explicitly marks token accounting unavailable.
Provider v3's `encrypted_state: false` widening permits reading the descriptor;
it grants no retention authority. The view remains read-only and states that
private retention requires owner approval and authenticated encryption. No
provider controls, provider calls, retention mutations, or automatic fallback
were added.

## Verification and remaining acceptance

`npm run test:effective-limits-browser` runs Chromium, Firefox and WebKit against
the real `RunsView` and `ContextServiceClient` with an in-memory workflow
projection and routed authenticated synthetic responses. It checks valid v3,
legacy v1, missing fields, tampering, stale pins, scoped routes, and absence of
credentials from DOM/storage. Its harness is production-built with the same
Vite settings and exact CSP as the application, and checks startup errors.
It also covers a valid descriptor followed by a rejected association refresh;
controlled-promise component tests cover older memory and session responses
arriving after that rejection.
This is synthetic browser/service-boundary
evidence. It is not a composed Console/Harness process or native/provider test.

Unit tests compare every executable row in original default/restricted/disabled
producer vectors, exact and one-over admission, and descriptor drift. The
empty-method disabled-session vector is explicitly invalid as a native
descriptor and is rejected; it is never represented as an attachable profile.
Run the pinned Node 24.16.0/npm install, contract-pin verifier, lint/typecheck,
unit tests, build, existing browser journeys and this dedicated browser suite.
Also run `node tools/generate-effective-limit-validators.mjs --check`.

Studio #119 stays open. Its acceptance remains partial:

| Acceptance | This slice | Remaining owner/integration work |
| --- | --- | --- |
| Final input accounting, Unicode, framing, schemas, pins and output reservation | None | Harness #107, tokenizer and final serialized input evidence |
| Deterministic eviction and overflow before invocation | None | Harness enforcement and zero-provider-call integration |
| Honest unavailable accounting | v1/missing/tampered/stale limits unavailable; bytes distinct from tokens | All tokenizer/history/provider-reported accounting states |
| Schema ceiling versus effective ceiling | Original producer vectors and exact/one-over consumer preflight | Composed owner enforcement and policy authoring |
| Model/adapter preview invalidation | Descriptor-bound preflight rejects changed descriptors | Budget preview/commit UI and owner usage/cost evidence |

Migration order remains: merge consumer readers, coordinate Console's served-v3
cutover, then align Harness consumer entries to exact accepted pins. Served v1
stays intentional until that coordination. Rollback may return advertisement to
v1 while retaining both readers; executable-limit display then stays unavailable.
